# AUT-357 — Preliminary inspection and disposition

## Goal

Give Warehouse and Technician users a fast, tablet-friendly preliminary inspection on an on-hand Machine, preserve its observations and private media as immutable history, and record a human disposition that coordinates the separate Production and Inventory state axes without implying full testing or QA Release.

## Ticket Summary

- Capture condition, bearing assessment, missing parts, damage, private evidence, recommendation, and reason.
- Support `repairable`, `hold`, `parts_only`, `scrap`, and `owner_review` dispositions.
- Preserve each inspection, decision, reason, decision maker, approver when required, media links, request, and timestamp.
- Coordinate current Production and Inventory states without merging them into one status.
- Treat bearing findings as human evidence only. Never auto-dispose a Machine from washer/dryer type, bearing noise, or any other observation.

## Expected Output

- The Machine detail page has a Preliminary Inspection panel for authorized staff and a complete newest-first inspection/decision history for every reader.
- A worker records one compact inspection and selects ready private Machine media as evidence.
- A Repairable disposition sets Production to `preliminary_passed` while Inventory remains `on_hand`.
- Hold and Owner Review leave Inventory `on_hand` and set Production to `blocked`.
- Parts-only and Scrap set Inventory to `scrapped` and Production to `blocked` only after Owner Admin approval.
- Staff Parts-only/Scrap recommendations route the current disposition to Owner Review; no dollar threshold or automatic scrap policy is encoded.
- Preliminary approval never means tested, repaired, cleaned, QA Released, listing-published, sold, or shippable.

## Product Decisions for This Slice

- Ticket vocabulary is canonical at the inspection boundary. `repairable` corresponds to Preliminary Passed; `parts_only` corresponds to Scrap for Parts. Needs Full Test/Awaiting Test belongs to later work-order tickets, and Return/Dispute is outside AUT-357.
- Bearing assessment values are observation-only: `no_concern_observed`, `concern_observed`, `not_applicable`, and `unable_to_assess`. No value implies a disposition.
- Condition, damage, bearing notes, missing-parts text, and reasons record observations without inventing model-specific pass/fail criteria.
- Warehouse, Technician/Cleaner, and Owner Admin may record an inspection and choose Repairable, Hold, or Owner Review. Only Owner Admin may finalize Parts-only or Scrap.
- A non-owner Parts-only/Scrap recommendation creates an immutable inspection plus an Owner Review decision. Owner Admin records a later final decision against that same latest inspection.
- Reinspection appends a new inspection; it never edits or deletes earlier inspections or decisions. Only the latest inspection may receive a new disposition. A Scrapped Machine cannot be reinspected in this ticket.
- Evidence is optional until approved checklist requirements define mandatory media. Selected evidence must already be a ready, private, Machine-targeted `preliminary_inspection` attachment for the same Machine.

## Non-Goals

- Do not implement full washer/dryer checklists, tests, defects, repairs, retests, cleaning, QA Release, work queues, or priority rules.
- Do not create recovered Part records, parts stock, salvage valuation, scrap accounting, notifications, Exception Cases, Return/Dispute, or reversal workflows.
- Do not change listing eligibility, publish listings, or permit shipment.
- Do not encode repair-cost thresholds, model-specific bearing rules, or required evidence counts.
- Do not add a standalone Production workspace or navigation item; AUT-357 lives on Machine detail.

## Codegraph Findings (live, this ticket)

- No Production module, contract, API, UI, or Production test exists.
- `MachineSchema` and the database currently permit only Production `not_started`; this ticket is the first real Production lifecycle seam.
- `InventoryOperations` is already consumed by Files/Imports and is the canonical cross-module boundary; extending it has a broad test blast radius, so keep the new method narrow and transaction-aware.
- `FilesOperations` has no same-Machine inspection-evidence query.
- `MutationRecorder.record(database, …)` is the canonical atomic audit/outbox path; inspection and state updates must reuse it.
- Machine detail is the smallest existing UI integration surface and already loads private files, permissions, QR, and synchronized server state.
- Existing web domain clients duplicate transport behavior; new Production code should extend `api-client.ts` rather than add another copy.

## Reuse Audit

Reused:

- Nest module/controller/service/repository boundaries and global authorization guard.
- Zod contracts, persisted role policy, PGlite migrations/tests, expected Machine versions, idempotency coordinator, mutation recorder, and append-only trigger pattern.
- Files-owned private uploads/grants, Machine attachments, `AttachmentsPanel`, route-state mapper, `useServerState`, online-state handling, and browser accessibility checks.

New code justified because:

- Production is an accepted domain with no current implementation.
- Inspection/evidence/decision history cannot be represented by mutable Machine state or generic attachments alone.
- Cross-lifecycle state coordination needs an explicit Inventory port and invariant tests.

Do not duplicate:

- Machine lookup/state writes, file access policy, role checks, idempotency fingerprints, audit/outbox writes, browser request handling, or attachment upload mechanics.
- Bearing/disposition policy in UI and API; the Production service owns it.

Escalated to human:

- None for implementation. Unresolved economic thresholds and detailed checklists remain deliberately unimplemented. The conservative owner-approval rule prevents an unapproved irreversible disposition.

## Constraints

- Production owns inspection/disposition behavior and persistence. Inventory owns current Machine lifecycle fields; Files owns attachments. Cross-module access uses exported ports only.
- Create the inspection, evidence links, decision, Machine state updates, audit entries, outbox jobs, and idempotency completion atomically.
- Read responses may compose Files metadata but never storage keys, bytes, grants, or raw sensitive payloads.
- Reject non-ready, wrong-purpose, wrong-Machine, duplicate, or over-limit evidence IDs without partial writes.
- Reject stale Machine versions and disposition attempts against a non-latest inspection without partial writes.
- Keep histories append-only and newest-first in responses. No update/delete endpoint exists.
- Preserve unrelated dirty-worktree changes and all existing additive API compatibility except the intentional internal `not_started` to `not_assessed` state migration.

## Tests Required

- Focused contract/unit tests for schemas, role permissions, state/disposition mapping, bearing non-automation, and client parsing.

- Web tests for permission visibility, form accessibility, offline gating, error recovery, evidence selection, and history rendering.

## Done Criteria

- Authorized staff can complete AUT-357 from the Machine page without a direct database or external-tool step.
- Every acceptance field and media relationship survives reload and remains immutable/auditable.
- Parts-only/Scrap cannot change Inventory state without Owner Admin approval, and bearing results never trigger an automatic decision.
- Inventory and Production states remain separate and match the specified mapping after every decision.

- Full workspace and desktop/tablet browser gates pass with no unrelated regressions or duplicated policy.
