# SF-08 — Shared-tablet application shell

## Goal

Turn the foundation web application into an installable, accessible, touch-first tablet shell for Warehouse and Technician/Cleaner users while preserving individual accountability and leaving the observed warehouse workflow open for later design.

## Ticket Summary

- Keep one responsive Next.js application/PWA; do not build a native tablet app or separate role applications.
- Add standards-based web app manifest, theme/viewport metadata, brand icons, and a small service worker registered by the app. Use standalone display and the configured platform origin.
- The service worker may cache only versioned public static assets and a generic offline page. It must never cache `/api/**`, authentication/session responses, protected HTML/RSC responses, files, imports, reports, QR labels, Machine/Load data, or request bodies. Protected navigation remains network-first and falls back to a non-personalized offline screen.
- Add a responsive shell with skip link, semantic landmarks, visible focus, current-page state, tablet side/top navigation, compact mobile navigation, and minimum 44x44 px interactive targets. Avoid hover-only affordances.
- Keep the signed-in person's name and role continuously visible. Preserve the existing prominent `Switch user / sign out` action and its warning when sign-out fails; never imply that handing over a tablet is safe before session removal succeeds.
- Make navigation permission-derived from the canonical shared policy. API authorization remains authoritative. Owner retains admin/import/operations access; Warehouse and Technician/Cleaner see only permitted foundation destinations.
- Add role-aware home screens:
  - Owner Admin: shortcuts to Imports, Loads, Machines, Team, Operations, and foundation health/review work.
  - Warehouse: expected Loads (where `receivedAt` is null), Machine Search, Scan, Locations, and a clearly marked `Pilot placeholder` for recent/assigned work.
  - Technician/Cleaner: Machine Search, Scan, allowed file access through Machine detail, and a clearly marked `Pilot placeholder` for assigned work.
- Do not create fake assignments, counts, checklist fields, testing/repair transitions, safety decisions, or warehouse status values. Placeholder cards explain that the detailed workflow will be defined after warehouse observation.
- Add a persistent Scan entry for every role with `inventory.machines.read`, using SF-07's authenticated fragment/manual resolver. Do not add a camera library in this ticket; device cameras can open printed QR URLs directly.
- Reuse existing foundation screens and make their primary flows tablet-safe: expected Load list/detail, Machine search/detail, QR resolution, Location selection/relocation where permitted, and photo/document list/upload where permitted.
- Add coherent loading skeletons, empty states, validation messages, permission-denied/not-found states, generic unavailable/retry states, and offline state. Errors must not expose internal details or discard form input unnecessarily.
- Add route-level `loading.tsx`, `not-found.tsx`, and protected error handling where appropriate. Treat a session failure as sign-in required; treat an API/network failure as unavailable/retry rather than redirecting every error to login.
- Add an online/offline status banner driven by browser events as a hint only. Server/API results remain authoritative after reconnect; no offline mutations or queued writes are allowed.
- Meet WCAG-oriented basics: keyboard traversal, programmatic labels, heading order, landmarks, status/alert live regions, color contrast, reduced-motion preference, non-color state text, and no trapped focus.
- Add browser-level tests with Playwright Chromium for desktop and a tablet viewport. Exercise real web/API/session boundaries using isolated test data; do not replace the browser test with component snapshots.

## Expected Output

- Installable PWA manifest/icons/service worker/offline page and safe registration.
- Responsive protected shell/navigation/account controls and role-aware home dashboards.
- Foundation Load/Machine/Location/File/QR screens refined for tablet, accessibility, and complete UI states.
- Playwright configuration, deterministic app/test setup, browser tests, CI/root command, and unit coverage for caching/navigation policy.

## Non-Goals

- Do not implement final intake, cleaning, testing, repair, parts, listing, sale, delivery, warranty, task assignment, timer, or technician checklist workflows.
- Do not cache private data for offline reading or support offline mutation/background sync.
- Do not add push notifications, GPS, camera scanning SDKs, kiosk/MDM configuration, biometrics, PIN shortcuts, or shared accounts.
- Do not redesign API domain behavior or create tablet-only backend endpoints solely for layout convenience.
- Do not introduce a new design system package, native wrapper, or separate frontend.

## Implementation Plan

2. Refactor the protected shell into accessible responsive navigation with current state and continuous user/role/handoff controls.
3. Build permission-derived role dashboards and pilot placeholders from existing foundation data/links.
4. Refine foundation screens and route boundaries for touch, accessibility, loading/empty/offline/permission/validation/retry behavior.
5. Add Playwright setup and desktop/tablet real-boundary journeys, wire CI/root command, then run all gates and the full Safe Foundation journey.

## Constraints

- No service-worker cache may persist operational/private/session content. Sign-out must clear this app's public/static cache version and no user-specific cache may exist.
- No offline mutation, optimistic queued write, or background sync. Disable mutation controls while offline with a clear reconnect message.
- UI role differences come from shared permissions; direct URLs still rely on server/API enforcement.
- Never use shared credentials. Every action retains the current individual user identity; the switch-user control stays prominent at all supported widths.
- Placeholder content is visibly non-functional and cannot be mistaken for real assignments or completed workflow logic.
- Responsive layout must work at 768x1024 portrait, 1024x768 landscape, common desktop widths, and 320 CSS px minimum without horizontal page scrolling.
- Touch target, focus, status/error semantics, and reduced-motion behavior are tested, not only visually asserted.
- Browser tests use isolated disposable database/storage and must not read/write user artifacts or depend on production secrets/services.

## Tests Required

- Root gates: format, lint, typecheck, unit, integration, browser, and production build.
- PWA: valid manifest/start URL/display/theme/icons; service-worker registration; offline document available; allowlist caches only public versioned assets; API/protected/auth/file/import/report/QR responses never cached.
- Navigation/home: exact Owner/Warehouse/Technician destinations and actions, active state, signed-in identity/role, prominent switch user, pilot labels, no unauthorized cards.
- Responsive/accessibility: tablet portrait/landscape and narrow viewport; no horizontal overflow; 44px primary targets; keyboard/focus order; landmarks/labels/headings/live regions; reduced motion; automated accessibility smoke where deterministic.
- States: route loading, empty expected Loads, no Machine results, invalid/revoked QR, validation error, permission denial, API unavailable/retry, offline banner/page, reconnect refresh.
- Browser journeys: each role signs in; Warehouse opens expected Load, searches/scans Machine, views files, and relocates when permitted; Technician reads the Machine/files but cannot manage Load/Location/QR; Owner reaches Import/Operations; user switch signs out and protected history cannot be reopened as the prior user.
- Regression: all SF-01 through SF-07 unit/integration behavior remains green and private data is absent from browser/service-worker caches and artifacts.

## Done Criteria

- The web app installs and runs as a coherent tablet PWA while remaining the same secure platform application.
- Warehouse and Technician users get clear, role-appropriate foundation paths and explicit pilot placeholders without invented workflow rules.
- Search/scan/detail/location/file flows are touch-accessible and handle empty, error, unavailable, offline, and permission states safely.
- User identity and switch/sign-out stay obvious on a shared device; cached content cannot expose a prior user's operational data.
- Real desktop/tablet browser tests and every root gate pass, including the program-level Safe Foundation journey.
