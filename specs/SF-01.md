# SF-01 — Application, database, and environments

## Goal

Create the runnable TypeScript workspace and verified development foundation for the Simply Clean Core Operations Platform. After this ticket, contributors must be able to install dependencies, run the web and API applications, exercise database readiness, and execute the canonical quality commands from the repository root without needing any later business module.

## Ticket Summary

Bootstrap a greenfield npm workspace containing a Next.js web application, NestJS API, and narrowly scoped shared packages for configuration, contracts, database access, and test support. Use PostgreSQL semantics through Drizzle ORM. Because Docker is unavailable in the current workspace, support PGlite for deterministic local/test execution and the normal PostgreSQL wire driver for deployed environments. Add configuration validation, health/readiness endpoints, structured privacy-safe logging, CI, and root-level lint/typecheck/test/integration/build commands.

## Expected Output

- A root npm workspace with deterministic lockfile and Node engine declaration.
- `apps/web`: a minimal branded Next.js application with a server health page that calls the API through a small typed client.
- `apps/api`: a NestJS modular application exposing liveness and database readiness endpoints.
- `packages/config`: canonical environment parsing and validation for server and public web configuration.
- `packages/contracts`: the first shared API contract for health/readiness responses.
- `packages/database`: Drizzle-backed database boundary supporting `pglite` and PostgreSQL drivers plus migrations.
- `packages/test-support`: reusable test environment/builders only where they encode shared test setup.
- Root documentation, safe `.env.example`, `.gitignore`, and GitHub Actions workflow.
- Canonical root commands: `npm run lint`, `npm run typecheck`, `npm test`, `npm run test:integration`, and `npm run build`.

## Non-Goals

- Do not implement users, authentication, roles, Loads, Machines, Locations, files, audits, imports, QR labels, or tablet workflows.
- Do not add microservices, queues, Redis, Kubernetes, Terraform, or cloud-provider-specific deployment configuration.
- Do not require Docker for local tests.
- Do not import code from `.codex-build/` or `build_workflow_doc.py`.
- Do not choose a hosting, authentication, or object-storage vendor in this ticket.

## Reuse Audit

Reused:

- Reuse the accepted modular-monolith and system-of-record decisions from the Reuse Map and ADRs.
- Reuse one environment parser from `packages/config` across the API, database package, and web server configuration.
- Reuse one database factory/readiness interface from `packages/database`; applications must not create direct driver clients.
- Reuse the health contract from `packages/contracts` in both API response typing and the web client.

New code justified because:

- No application workspace or reusable product code exists.
- A PGlite adapter is needed because Docker is not available locally while PostgreSQL behavior remains required.
- A PostgreSQL wire adapter is needed for staging/production and CI parity.

Do not duplicate:

- Environment validation inside individual applications.
- Database connection setup inside controllers, pages, or tests.
- Health response shapes in web and API packages.
- Root command definitions inside ad hoc shell scripts.

Escalated to human:

- None. Hosting, production database vendor, and authentication provider remain intentionally undecided and are not required for this ticket.

## Implementation Plan

1. Create the npm workspace, root configs, safe ignore rules, and README.
2. Add the shared configuration and health-contract packages with unit tests.
3. Add the database package with explicit `pglite` and `postgres` driver selection, a no-domain bootstrap migration if required, readiness query, and cleanup API.
4. Create the NestJS API with dependency injection for configuration/database, privacy-safe Pino logging, liveness, and readiness endpoints.
5. Create the Next.js web application with a simple operational landing page and a server-side health client using the shared contract.
6. Add unit tests plus API/database integration tests that run locally through PGlite.
7. Add a CI workflow that additionally proves the PostgreSQL wire driver against a service container.
8. Run all root commands, correct failures, and document the exact workflow.
9. Refresh the codegraph index after implementation so the architect can review current symbols.

## Constraints

- Use npm workspaces and commit `package-lock.json`.
- Use strict TypeScript and ESM-compatible package boundaries.
- Use currently supported stable package releases compatible with the installed Node runtime; do not use prerelease versions.
- Prefer boring explicit configuration over a monorepo task orchestrator at this size.
- `DATABASE_DRIVER=pglite` must be the safe local/test default; deployed environments must reject accidental PGlite use unless explicitly allowed.
- `DATABASE_URL` is required for the PostgreSQL driver and must never be printed.
- PGlite file data must live under a gitignored local-data directory; tests use isolated disposable instances.
- Health liveness must not depend on the database. Readiness must report database availability without leaking connection details or stack traces.
- Structured logs may include correlation IDs, route, status, and duration but not secrets, credentials, PII, request bodies, or query parameters by default.
- Generated framework output must be minimized and aligned with the workspace conventions.
- Preserve existing API contracts unless explicitly required.
- Follow `AGENTS.md`, including the reuse-vs-inline rule.
- Keep changes scoped to this ticket.

## Tests Required

- `npm run lint`
- `npm run typecheck`
- `npm test`
- `npm run test:integration`
- `npm run build`
- API integration assertion: `GET /health/live` succeeds without database readiness.
- API integration assertion: `GET /health/ready` succeeds with PGlite and returns the shared contract.
- Database integration assertion: production wire adapter performs a readiness query when `DATABASE_DRIVER=postgres` and CI PostgreSQL is available.
- Configuration assertions: invalid driver/environment combinations fail before application startup and error messages never include secret values.

## Done Criteria

- A new contributor can follow `README.md` and start the web/API development applications.
- Web and API use the shared contract and canonical configuration/database boundaries.
- Local verification requires no Docker and all five root commands pass.
- CI is configured to verify both PGlite and PostgreSQL wire paths.
- No credentials, local database files, generated builds, or private artifact outputs are committed.
- No application code reuses the existing document/presentation generators.
- Codegraph is refreshed and no duplicate configuration/database/health implementations are introduced.
