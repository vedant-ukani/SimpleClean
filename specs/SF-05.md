# SF-05 — Audit history and reliable internal events

## Goal

Make every consequential foundation mutation attributable and searchable, and establish one PostgreSQL-backed reliability boundary for internal events, retryable background work, and idempotent API creation. Domain state, audit, and its outbox event must commit together; failed event delivery must remain visible and safely retryable by an Owner Admin.

## Ticket Summary

- Add an Operations module that owns the cross-domain audit log, transactional outbox worker, idempotency records, Owner APIs, and their contracts.
- Export a small `MUTATION_RECORDER` port. An owning repository calls it with its existing `DatabaseExecutor` inside the same transaction as a successful mutation. The recorder appends both one audit entry and one outbox work item; it never starts a disconnected transaction.
- Keep existing specialized history (`identity_security_activity`, Machine identity/location history, and `file_activity`). The central audit log is the cross-domain index, not a replacement for detailed domain evidence.
- Audit actor kind/user, action, target type/ID, request/correlation ID, timestamp, and a privacy-safe structured summary containing field names/outcomes only. Do not persist raw request/response bodies, filenames, emails, serial values, tokens, credentials, file bytes, stack traces, or arbitrary exception text.
- Cover all existing successful domain mutations: staff profile/role/active/session actions; Load create/update; Location create/update/deactivate; Machine create/identity update/verification/conflict/relocation; file attachment requested/ready/failed/abandoned. Read actions, rejected mutations, authorization denials, grant issuance/downloads, and health checks stay out of the central mutation audit.
- Define stable dotted action/event names owned by the producing module (for example `inventory.machine.created`). Do not use UI labels as identifiers.
- Use one `platform_outbox_job` table as the transactional outbox and durable delivery queue. Store only event type, target reference, actor/request identifiers, safe summary, state, attempt count, availability, lease/version, timestamps, and a safe error code.
- Add a worker service with a bounded `runOnce`/drain operation. Atomically claim eligible queued/retry-wait or expired-lease rows, publish them through an injected internal-event dispatcher, and compare-and-set success/retry/dead-letter using the lease/version. Concurrent workers must not process the same active lease.
- Default dispatch to an internal handler registry; zero subscribers is a valid delivery. Tests can inject a failing handler/dispatcher. Never dynamically execute a handler name from database content.
- Use configurable maximum attempts, lease duration, polling interval, and backoff base. Disable automatic polling in tests; start/stop it through Nest lifecycle in normal environments without preventing graceful shutdown.
- On handler failure, store an allowlisted/sanitized code only. Retry after exponential bounded delay and move to `dead_letter` after the configured maximum. An Owner Admin may requeue only a dead-letter row; requeue itself is audited and version-checked.
- Add an idempotency coordinator/table that stores a hash of the key, a canonical request fingerprint, scope, and completed target reference. Never store the raw key or body.
- Require `Idempotency-Key` on current retry-prone Inventory create APIs: Load, Location, and Machine. The web client generates a UUID once per submit attempt and reuses it for retries. Same scope/key/fingerprint returns the existing business record; the same key with a different fingerprint returns conflict. Concurrent duplicates produce one record.
- Future Import, QR, webhook, and integration mutations must reuse the recorder/idempotency ports; do not add speculative Import/QR records in this ticket.
- Add Owner Admin Operations UI with recent/filterable audit history, dead-letter/retry-wait work, attempt/error-code visibility, and a guarded Retry action. Other roles cannot call or see it.

## Expected Output

- `apps/api/src/modules/operations` containing contracts-facing service/controller, mutation recorder, audit/outbox/idempotency repository logic, internal dispatcher port/registry, and durable worker.
- PostgreSQL migrations/schema for append-only audit entries, outbox jobs, and idempotency records, including constraints/indexes and immutable audit protection.
- Existing Identity, Inventory, and Files mutations record central audit/outbox entries in their existing transactions.
- `GET /operations/audit`, `GET /operations/jobs`, and `POST /operations/jobs/:jobId/retry` Owner-only APIs.
- `/admin/operations` Owner page and navigation with audit filters and failed-work retry.
- Runtime configuration, shared contracts/permissions, deterministic tests, and local operating documentation.

## Non-Goals

- Do not implement external providers, webhooks, notifications, scheduled file retention, OCR, Import, QR, Production, Listing, Sales, or Logistics handlers.
- Do not replace specialized domain history with a generic event-sourcing model.
- Do not store full domain snapshots or arbitrary event payloads in audit/outbox/idempotency tables.
- Do not guarantee exactly-once external side effects. Provide at-least-once delivery plus stable event/job IDs for future handler idempotency.
- Do not add Redis, Kafka, RabbitMQ, a hosted queue, a second database client, or a microservice.
- Do not expose a public worker-drain endpoint or allow arbitrary event/job creation from HTTP.

## Codegraph Findings (live, this ticket)

- No central audit, outbox, job, dispatcher, idempotency table, or worker currently exists.
- `InventoryRepository`, `IdentityRepository`, and `FilesRepository` already own the relevant transactions; this is the only safe place to add atomic recording.
- `identity_security_activity`, Machine evidence/verification/location history, and `file_activity` are domain-specific immutable records and must remain canonical for their detail.
- `InventoryService` is the existing module boundary; Load/Location methods currently lack actor context while Machine methods already carry it.
- Request logging already creates a correlation ID and omits bodies/query values. Operations must reuse it rather than generate unrelated audit IDs.
- Web create helpers currently send no idempotency header and are called from Load, Location, and Machine submit components.

## Constraints

- A successful audited domain mutation, central audit row, and outbox job commit together or not at all.
- Audit rows are append-only. Outbox/idempotency state may change only through Operations use cases with expected lease/version checks.
- Domain modules call an explicit Operations port and never write Operations tables directly; Operations never writes domain tables.
- Actor is the authenticated persisted profile; system work uses explicit `system` actor kind rather than a fake user.
- Summaries contain controlled field names/outcomes only. Error persistence uses safe codes; full errors may not leak to API responses or storage.
- Worker claims are bounded and lease-based. Expired leases are reclaimable; active leases are not; completion/failure from a stale lease is ignored.
- Backoff and maximum attempts are configured, finite, and deterministic under an injected clock in tests.
- Idempotency scope includes operation and authenticated actor where appropriate. Compare canonical parsed input hashes, not raw JSON formatting.
- A raw idempotency key is accepted only in its header, excluded from logs, hashed before storage, and never returned by list APIs.
- Existing public response shapes remain unchanged. A duplicate accepted create returns the one existing resource.

## Done Criteria

- Every successful current foundation mutation has one privacy-safe central audit record and one atomic outbox job without weakening specialized histories.
- Retried Load/Location/Machine creates return one business record; key misuse is rejected and concurrent duplicates cannot fork records.
- The worker safely claims, retries, recovers leases, dead-letters, and supports audited Owner requeue without duplicate active processing.
- Owner Admin can review audit history and failed work; Warehouse/Technician users cannot.
- Future modules have one documented recorder/idempotency/dispatcher boundary to reuse.
- Full root gates pass and no duplicate transaction, authorization, audit, idempotency, lease, retry, or privacy logic is introduced.
