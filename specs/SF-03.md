# SF-03 — Loads, Machines, Locations, and operational identity

## Goal

Create the minimum authoritative Inventory and Intake records needed to receive a group of equipment, give each physical Machine an immutable platform identity, find it, and know where it is. Workers must be able to create incomplete provisional records quickly without turning unknown plate facts into guesses or collapsing inventory and production into one status.

## Ticket Summary

- Add one Inventory and Intake API module owning Acquisition Loads, Machines, Inventory Locations, machine identity evidence/revisions, identity claims/conflicts, and location history.
- Reuse the SF-02 Identity module for User/Profile, current actor, roles, and server authorization. Do not create a second user/profile table.
- Generate an immutable UUID for every Load, Machine, Location, and history/evidence record. Machine ID never depends on manufacturer, model, serial, spreadsheet row, or an external system.
- Allow a Machine to be created under a Load with only `machineType`; all nameplate-derived fields may remain null.
- Machine current facts: machine type, manufacturer, model, serial, voltage, phase, fuel, source Load, current Location, identity verification state, inventory state, production state, version, and timestamps.
- Controlled foundation values:
  - machine type: `washer`, `dryer`, `other`;
  - phase: `single_phase`, `three_phase`, or null/unknown;
  - fuel: `gas`, `electric`, `steam`, `other`, or null/unknown;
  - identity verification: `provisional`, `verified`, `conflict`;
  - inventory state: `expected`, `on_hand`;
  - production state: `not_started` only in this ticket.
- Keep inventory and production state in separate columns/contracts even though SF-03 exposes only the safe foundation values. Later owning modules extend their controlled transitions.
- Store each submitted identity snapshot as immutable evidence with raw values, source kind, actor, request ID, and timestamp before updating the current normalized Machine view. SF-03 source kinds are `manual` and `other`; SF-06 will add spreadsheet provenance through the same module interface.
- Verification is an explicit command, not a side effect of entering a serial. It requires manufacturer and serial, normalizes them for matching, and obtains one unique database-backed identity claim for that manufacturer/serial scope.
- If another Machine already owns the normalized manufacturer/serial claim, keep both Machines, mark the attempted Machine `conflict`, link the conflicting Machine ID, preserve the attempted evidence, and return a visible conflict response. Never silently merge or create two verified claims.
- Correcting identity fields returns the Machine to `provisional`, clears its conflict link, and releases its prior verified claim transactionally. Verification may then be attempted again.
- Inventory Location contains a unique human-readable code, name, active flag, version, and timestamps. Locations are deactivated, not deleted, once referenced.
- Every relocation records from/to Location, actor, request ID, Machine version, and timestamp in immutable location history.
- Acquisition Load contains an immutable ID, required display name, optional source name/reference, optional expected-arrival timestamp, optional received timestamp, version, and timestamps. Cost allocation, seller Party linkage, and logistics state are later modules.
- Use optimistic concurrency (`expectedVersion`) for Load edits, Location edits/deactivation, identity edits, verification, and relocation.
- Add paginated Machine search by internal ID, manufacturer, model, serial, Load name/reference, and Location code/name. Exact ID and exact serial matches rank before partial text matches.
- Provide simple protected web views for Loads, Machine search/details, and Locations. Owner Admin can manage Loads and Location definitions; Owner Admin and Warehouse can create/update/verify/relocate Machines; Technician/Cleaner can search and read only.

## Expected Output

- Protected `/loads`, `/loads/[loadId]`, `/machines`, `/machines/[machineId]`, and `/locations` screens.
- Inventory APIs under `/inventory/loads`, `/inventory/machines`, and `/inventory/locations` with validated shared contracts.
- PostgreSQL migrations for Loads, Machines, identity evidence/claims, Locations, and location history.
- A reusable Inventory service interface that later import, photo, QR, production, and listing modules can call without writing Inventory tables directly.
- Integration tests proving provisional creation, search, relocation history, duplicate identity conflict, authorization, validation, and optimistic concurrency.

## Non-Goals

- Do not finalize intake checklists, OCR, photos/documents, QR labels, cost allocation, preliminary inspection, production workflow, parts, pricing, listings, reservations, or sales.
- Do not add a Party/CRM seller record. `sourceName` and `sourceReference` are temporary nullable Load facts until the owning Party/Acquisition modules exist.
- Do not infer manufacturer/model/serial/voltage/phase/fuel from each other or from a Machine type.
- Do not add final inventory, production, listing, sales, payment, or shipment lifecycle values.
- Do not hard-delete referenced Locations, Loads, Machines, identity evidence, claims/history, or relocation history.
- Do not expose raw repository/database access to later modules; they call the Inventory service interface.
- Do not implement SF-05's platform-wide audit/outbox. Domain identity revisions and location history satisfy SF-03 traceability and become inputs to the later audit foundation.

## Implementation Plan

1. Extend shared permissions/contracts and test all role grants: Owner Admin manages all; Warehouse reads Loads/Locations and manages/verifies/relocates Machines; Technician/Cleaner reads Machines and Locations only.
2. Add database tables/checks/indexes. Use a unique identity-claim table keyed by normalized manufacturer plus serial, with a unique Machine link, so concurrent verification cannot produce duplicate verified identities.
3. Implement module-local normalization, repository, and Inventory service. Preserve every submitted identity snapshot before changing current facts.
4. Implement Load create/list/get/update, Location create/list/get/update/deactivate, Machine provisional create/get/update/search, verify, and relocate use cases.
5. Map validation to `400`, missing records to `404`, permission failure through the global `403`, stale versions to `409`, and identity claim conflict to `409` with the conflicting Machine ID and persisted `conflict` state.
6. Add integration tests for permissions, nullable facts, immutable IDs/history, normalized duplicate detection, concurrent verification, concurrency versions, inactive locations, and relocation history.
7. Add role-aware web navigation and simple pages/forms. Display unknown values as “Not recorded,” conflicts explicitly, and never imply that provisional identity is verified.
8. Run root formatting, lint, typecheck, unit, integration, and build gates.

## Constraints

- Follow `AGENTS.md` and keep all mutation rules in the owning service/repository boundary.
- IDs are opaque strings in contracts and UUIDs in storage; client input cannot choose a Machine ID.
- Keep serial and voltage as strings. Trim/collapse whitespace and case-fold only dedicated match keys; preserve display/raw values exactly enough to audit user evidence.
- Null means unknown. Do not persist strings such as `unknown`, `n/a`, or guessed defaults for nullable plate facts.
- A `verified` Machine must own exactly one manufacturer/serial identity claim; a `conflict` or `provisional` Machine owns none.
- Updating identity facts, verifying, and relocating each increment Machine version exactly once.
- Relocation requires an active destination Location and records history in the same transaction as current-location change.
- A Load with Machines and a Location referenced by history cannot be deleted.
- Search is bounded and paginated; escape/parameterize all query text and never interpolate raw input into SQL.
- Mutation/history records include the authenticated actor and request/correlation ID but no session token, cookie, password, or unrelated PII.
- UI permission checks control presentation only; API permissions remain authoritative.

## Done Criteria

- An authorized Warehouse user can create a provisional Machine under an Owner-created Load with nullable plate facts, assign/relocate it to an active Location, and retrieve it by immutable ID.
- Machines are searchable by the required identity/load/location terms and results clearly show provisional, verified, or conflict state.
- One normalized manufacturer/serial identity can belong to only one verified Machine, including under concurrent requests; conflicts remain visible and reviewable without merging records.
- Every identity submission and relocation is attributable and immutable; critical mutations reject stale versions.
- Inventory and production states are separate in schema, contracts, API, and UI.
- Owner Admin, Warehouse, and Technician/Cleaner receive the specified server permissions and matching navigation/actions.
- Root formatting, lint, typecheck, unit, integration, and build commands pass with no duplicate User/Profile, policy, normalization, or database client introduced.
