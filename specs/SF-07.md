# SF-07 — QR label generation and scan lookup

## Goal

Give every created Machine a durable, printable, revocable QR identity that opens its authorized platform summary without encoding a Machine ID, serial, customer, price, or other business data.

## Ticket Summary

- Keep QR identity under Inventory ownership (`apps/api/src/modules/inventory/qr/**`) because it identifies Machines. Do not create a parallel Machine lookup domain or let React generate/security-check labels.
- Add signed opaque QR tokens. The payload contains only a version, random Label ID, and HMAC signature; it contains no Machine ID or business fact. Sign with a dedicated validated `QR_SIGNING_SECRET`, never the authentication secret.
- Encode an absolute configured platform URL whose token is in the URL fragment (`/scan#<token>`). Fragments are not sent in HTTP requests/referrers. The client reads it and submits the token in a protected POST body; request logging never records bodies.
- Store Label ID, Machine relationship, random human fallback code, state, version, issuer/revoker, and timestamps. Do not store the signature/token because it is deterministically regenerated from Label ID plus the QR secret.
- Use cryptographically random UUID Label IDs and random uppercase Crockford-style fallback codes with enough entropy to resist guessing. Enforce unique Label ID/fallback code and one active label per Machine in PostgreSQL.
- Label states are `active` and `revoked`. Reissue atomically revokes the current label and creates a new one; the old token immediately stops resolving. Preserve every row as label history; never rewrite a revoked token into a new Machine.
- Allow Owner Admin and Warehouse users to create, print/download, revoke, and reissue labels. Technician/Cleaner may resolve labels and view permitted Machine summaries but may not manage labels.
- Require the Machine to exist through the Inventory service boundary. No label can be issued for an absent Machine. Machine deletion is not part of this foundation.
- Require `Idempotency-Key` for create and reissue. Extend the Operations coordinator target union with `qr_label`; same key/fingerprint returns the existing label and concurrent requests cannot create two active labels.
- Create/revoke/reissue in a database transaction with privacy-safe central audit/outbox actions (`inventory.qr_label.created`, `.revoked`, `.reissued`). Use expected version for revoke/reissue. Do not include token, signature, fallback code, serial, or Machine facts in summaries.
- Keep append-only specialized QR activity for `created`, `printed`, `resolved`, `revoked`, and `reissued`, with label/Machine/actor/request/time only. Print and scan reads do not create outbox work. Protect the activity table with the established immutable-trigger convention.
- Resolve either a signed QR token or a manually entered fallback code through `POST /inventory/qr-labels/resolve`. Validate syntax before lookup, verify HMAC with constant-time comparison, require an active label, then return the canonical `MachineDetail` allowed by `inventory.machines.read`. Invalid/revoked/unknown values return one generic not-found response.
- Generate printable SVG on demand using a maintained QR encoder. The label contains the QR image, `Simply Clean Equipment`, and the fallback code only. Do not print serial, model, price, source, customer, location, or internal Machine ID.
- Return printable SVG with private/no-store headers, a generated safe filename, explicit dimensions/viewBox, and accessible text. Record a `printed` activity only after an authorized active label is successfully rendered.
- Add a Machine detail QR panel showing active/history state and guarded Create, Download/Print, Revoke, and Reissue actions. Add `/scan` as an authenticated, touch-friendly client page that accepts the URL fragment or manual fallback and shows loading, invalid/revoked, permission, and Machine-summary states.
- A signed token is a lookup reference, not authorization. Every resolution, print, list, and management request still requires a current persisted user/session and canonical permission check.

## Expected Output

- Inventory-owned QR service/repository/controller components with an explicit signer/renderer boundary.
- Shared QR contracts, permissions, operations actions/target, config, database tables/migration, and tests.
- Protected QR controls on Machine detail plus `/scan` resolution/manual-entry UI and same-origin clients.
- Maintained QR encoding dependency isolated behind a renderer adapter; no custom QR matrix implementation.

## Non-Goals

- Do not implement public/anonymous Machine pages, customer tracking, NFC/RFID, bulk label sheets, Bluetooth printers, camera SDKs, native apps, or final intake workflow.
- Do not embed or fetch serial/model/customer/price/location in the QR payload.
- Do not make a label token a bearer authorization credential.
- Do not store generated SVG/base64 in PostgreSQL or object storage; render deterministically on authorized request.
- Do not add externally observable scan analytics, GPS, notifications, or retention deletion.

## Constraints

- The QR payload and printed text contain no Machine ID or business data; only the signed opaque label reference appears.
- QR signature comparison is constant-time after strict length/encoding validation. Never log tokens, signatures, URL fragments, fallback codes, or secrets.
- QR secret must be at least 32 characters/high entropy; deployed environments reject placeholders and require HTTPS public origin. Secret rotation invalidates existing signatures and must be an explicit operational migration/reissue.
- Exactly one active label may exist per Machine. Revoked labels never resolve or print. Reissue is one transaction.
- Fallback resolution is authenticated and uses a non-sequential random code; unknown/revoked/malformed inputs are indistinguishable to callers.
- Activity is append-only and privacy-safe. Central audit/outbox covers consequential lifecycle mutations, not every scan.
- Print SVG is escaped, bounded, deterministic, and private/no-store. No arbitrary text enters SVG markup.
- Raw Machine UUID routes remain protected, but QR resolution never accepts a Machine UUID as a token/fallback.

## Tests Required

- Root gates: format, lint, typecheck, unit, integration, and production build.
- Config/contracts: secret/origin validation, state/input/output schemas, permissions, action/target unions.
- Signer: deterministic regeneration, valid/altered/malformed/version/length cases, no Machine facts, and constant-time comparison path.
- Renderer: decodable QR payload, minimal safe text, SVG escaping/headers/dimensions, no serial/model/Machine ID.
- Lifecycle: Machine required, one active label, sequential/concurrent idempotent create, versioned revoke, atomic reissue, old-token rejection, new-token success, immutable history/activity.
- Resolution/security: signed fragment token and fallback success for each reading role; anonymous/unauthorized/revoked/unknown/guessed IDs fail; generic failures; token/fallback absent from audit/log-shaped records.
- Operations: lifecycle mutation + central audit/outbox commit together and roll back together; scan/print activity does not enqueue work.
- Web: role controls, Machine label state/history, print action, `/scan` fragment/manual loading/error/success, logout/user identity preserved.
- Regression: SF-02 through SF-06 auth, Inventory, Files, Operations, and Import behavior remain green.

## Done Criteria

- An authorized user can create, print, scan, manually resolve, revoke, and reissue a Machine label.
- A revoked or forged token never resolves; random labels/fallbacks do not expose sequential identifiers or bypass authorization.
- Payload, SVG, database, audit, activity, and logs contain only the intended privacy-safe references.
- Concurrent/retried management cannot create duplicate active labels, and all histories remain attributable.
- Full root gates pass without duplicate Machine, auth, signing, idempotency, or audit logic.
