# SF-02 — Authentication and role permissions

## Goal

Require an individual staff sign-in for every protected Simple Clean surface and enforce the same Owner Admin, Warehouse, and Technician/Cleaner policy on the server. The pilot must support secure credential sessions, safe shared-tablet handoff, role-aware navigation, and Owner Admin user administration without placing authorization decisions in the browser.

## Ticket Summary

- Use Better Auth's email/password and database-backed session support; do not implement password hashing, credential verification, cookie signing, or session token generation locally.
- Mount the Better Auth handler in the NestJS API under `/auth/*`; browser calls reach it through a same-origin Next.js `/api/*` proxy/rewrite.
- Use one business tenant. Do not add Better Auth's organization plugin or a multi-tenant membership model.
- Define exactly three canonical application roles: `owner_admin`, `warehouse`, and `technician_cleaner`.
- Define canonical permission identifiers and the role-to-permission policy once in `packages/contracts`. SF-02 needs `platform.access`, `identity.self.read`, `identity.users.read`, and `identity.users.manage`; later tickets extend the same policy rather than create local role checks.
- Persist the application role and active/inactive state in the Identity module, linked one-to-one to the Better Auth user. Better Auth remains responsible for credentials and sessions; the platform remains responsible for operational authorization.
- Resolve every protected request from the signed session and current persisted identity record. Ignore client-supplied roles and permissions.
- Provide login, logout, current-user, and Owner Admin user-management behavior. User management includes list, create, change role, activate/deactivate, and revoke all sessions.
- Deactivation and role changes revoke existing sessions so stale privileges cannot continue.
- Record privacy-safe identity security activity for successful sign-in, logout, user creation, role change, activation/deactivation, session revocation, and authorization denial. Store identifiers/action/request ID only; never store passwords, session tokens, cookies, raw authorization headers, or complete request bodies.
- Provide a deliberate test/bootstrap user provisioning command. Read the password from an environment variable or hidden input, never a command-line argument or source-controlled default.
- Keep `/health/live`, `/health/ready`, `/login`, and Better Auth's required sign-in routes public. All operational pages and APIs are protected.

## Expected Output

- A working staff login at `/login` and protected signed-in home at `/`.
- Owner Admin-only team management at `/admin/users`.
- Auth endpoints under `/auth/*` plus application identity endpoints under `/identity/*`.
- Database migrations for Better Auth records, platform identity profiles, and identity security activity.
- One shared authorization policy consumed by the API and web navigation.
- A safe provisioning command documented in the README and `.env.example`.
- Integration tests proving anonymous denial, login/logout, server-side role enforcement, session revocation, and role denial.

## Non-Goals

- Do not add customer, distributor, seller-portal, social-login, SSO, organization, or multi-tenant authentication.
- Do not implement MFA in this pilot ticket; keep the auth adapter replaceable so elevated-account MFA can be added before production exposure.
- Do not implement Loads, Machines, Locations, files, imports, QR labels, or final tablet workflows.
- Do not grant future operational permissions merely because a role is expected to need them. Later owning tickets add explicit permissions.
- Do not build an email invitation or password-reset delivery integration. Owner Admin creates pilot accounts and securely communicates the initial password out of band.
- Do not create a second database client, run migrations during API boot, or make liveness depend on authentication/database readiness.
- Do not use localStorage for sessions or authorization data.

## Reuse Audit

Reused:

- `createDatabase` and `DATABASE_CONNECTION` for the only runtime database connection.
- `parseServerEnvironment` for all auth runtime settings.
- Zod contract/export conventions in `packages/contracts`.
- Structured logging redaction and request correlation from `apps/api/src/platform/logging.ts`.
- PGlite integration-test environment and root validation commands.
- Better Auth for credential hashing, secure tokens/cookies, session lifecycle, and auth endpoint semantics.

New code justified because:

- The repository has no Identity module, authorization policy, auth adapter, user management, or login UI.
- A reusable database handle is required by every later repository and must extend the established connection rather than create parallel clients.
- Platform roles are domain decisions and must not be hidden inside UI conditionals or a vendor-specific organization model.

Do not duplicate:

- Password hashing, cookie/session token generation, or credential verification.
- Role-to-permission maps in API controllers or React components.
- Session parsing in individual controllers; use the shared identity request context/guard.
- Database clients or runtime migration behavior.

Escalated to human:

- None. The three roles and single-business scope are already accepted. MFA and external invitation delivery remain explicitly deferred, not silently decided.

## Implementation Plan

1. Add Better Auth and required peer dependencies; generate/inspect its PostgreSQL schema, then check the resulting migration into the existing explicit migration chain.
2. Extend validated configuration with a strong auth secret, public auth base URL/trusted origin, and session duration. Allow deterministic test-only values but reject missing/weak deployed secrets.
3. Extend `DatabaseConnection` with the canonical Drizzle query handle while keeping driver creation, migration, readiness, and shutdown in the existing factory.
4. Add shared role/permission schemas and pure policy helpers. Role checks call the policy; UI consumes the same policy only for presentation.
5. Build the Identity module: Better Auth configuration and handler, profile repository/service, request identity resolution, permission guard/decorator, and privacy-safe security activity.
6. Implement `/identity/me` and Owner Admin-only `/identity/users` operations. Changing role, deactivating a user, or explicitly revoking sessions invalidates all active sessions for that subject.
7. Add a provisioning command that creates or updates a pilot user through the same identity service and rejects defaults/secret disclosure.
8. Add a same-origin Next.js API proxy, login screen, protected shell, logout/user-switch action, role-aware navigation, and Owner Admin team-management page.
9. Add unit/integration tests using migrated isolated PGlite. Verify actual cookies and persisted sessions rather than stubbing authorization at the controller boundary.
10. Run the full repository gates and confirm liveness still succeeds when the database/auth dependency is unavailable.

## Constraints

- Preserve existing health contracts and explicit migration behavior.
- Follow `AGENTS.md`, including server-side authorization and reuse-vs-inline rules.
- Better Auth is an adapter inside Identity, not the location of platform business permissions.
- Normalize email using the auth library's supported behavior; do not add home-grown password or token cryptography.
- Cookies must be `HttpOnly`, `SameSite=Lax` or stricter, and `Secure` outside local development/test. Use finite sessions (eight hours by default) and server-side revocation.
- Do not reveal whether an email exists in unauthenticated error details beyond Better Auth's safe defaults.
- Return `401` for missing/invalid sessions and `403` for authenticated users lacking permission.
- Role changes and deactivation are Owner Admin-only and may not remove/deactivate the final active Owner Admin.
- User administration must use optimistic/versioned or transactional checks so concurrent changes cannot violate the final-owner invariant.
- Do not log passwords, auth headers, cookies, session tokens, raw request bodies, or full email lists. Security activity metadata must be allow-listed.
- Keep all schema/migration changes compatible with PostgreSQL and PGlite.
