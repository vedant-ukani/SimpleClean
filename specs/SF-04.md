# SF-04 — Private photos and document storage

## Goal

Let authorized staff attach trustworthy nameplate photos, arrival-condition photos, receipts, and documents to a Machine or Acquisition Load. PostgreSQL remains authoritative for metadata and relationships, while file bytes stay private behind a replaceable storage adapter and short-lived, one-time access grants.

## Ticket Summary

- Add a Files API module that owns attachment metadata, file access grants, file activity, content policy, and storage adapters.
- Store bytes through a `StorageAdapter`; provide a deterministic local-filesystem implementation and an S3-compatible implementation using AWS SDK for JavaScript v3 commands. No controller or domain module talks directly to a bucket or filesystem.
- Add shared file permissions: `files.read`, `files.write`, and `files.manage`. Owner Admin receives all; Warehouse receives read/write; Technician/Cleaner receives read/write for Machine attachments only. Target-specific authorization must also require the role's existing Machine or Load read permission.
- Attach a file to exactly one Machine or one Acquisition Load using explicit nullable foreign keys plus a database one-target check. Do not use an unvalidated polymorphic string ID.
- File purposes: `nameplate`, `arrival_condition`, `document`, `receipt`, and `other`. `nameplate` is Machine-only. Other purposes may attach to a Machine or Load during this foundation.
- File states: `pending_upload`, `ready`, `failed`, and `abandoned`. Only `ready` files can receive download grants.
- Store generated opaque storage keys, original filename as display metadata only, declared/detected media type, byte count, SHA-256 checksum, uploader, target, purpose, state, safe failure code, timestamps, and version.
- Supported content in this ticket: JPEG, PNG, WebP, and PDF. Images are valid for photo purposes; PDF is valid for `document`, `receipt`, or `other`. Detect the actual type from file bytes and reject a mismatch, unsupported content, or size over the configured maximum.
- Never use the client filename as a storage key or filesystem path. Sanitize it only when returning `Content-Disposition`.
- Upload flow:
  1. authorized caller requests an upload grant with target, purpose, filename, declared media type, and declared size;
  2. service validates target existence/access and creates `pending_upload` metadata plus a short-lived one-time opaque grant;
  3. caller posts bounded multipart bytes to a fixed endpoint using the grant in an `x-file-grant` header and the same signed-in session;
  4. API detects content, computes SHA-256, writes the generated key through the adapter, verifies object head metadata, and marks the record `ready` with activity in a database transaction;
  5. failure leaves a visible safe `failed`/`pending_upload` state and deletes a partial object when possible.
- Download flow: an authorized caller requests a short-lived, one-time grant for a `ready` file, then downloads from a fixed same-origin endpoint with the token in a query parameter. Request logging already strips query strings; never place a token in a logged path.
- Store only SHA-256 hashes of grant tokens. Bind each grant to file, operation, issuing user, expiration, and one-time consumption.
- Provide Owner Admin incomplete-file review and cleanup. Expired pending uploads can be marked `abandoned`; any corresponding object is removed. Automatic scheduling waits for SF-05 durable jobs.
- Record immutable privacy-safe file activity for upload grant, ready upload, failed upload, download grant, download, and abandonment. Do not record bytes, tokens, filenames, cookies, or request bodies in activity.
- Add Machine and Load attachment panels for list/upload/download. UI grants are convenience only; the API rechecks current session, role, target access, state, expiry, token hash, and issuer.

## Expected Output

- Files API under `/files` with create-upload-grant, upload-content, list, create-download-grant, download-content, incomplete-review, and abandon/cleanup operations.
- `apps/api/src/modules/files` with one service interface and local/S3 adapter implementations.
- Migrations for file metadata, hashed access grants, and immutable file activity.
- Validated storage configuration for local/test and S3-compatible deployed storage.
- Machine and Load pages that show attachments and permit role-appropriate uploads/downloads.
- Integration tests proving private access, policy validation, object/checksum agreement, one-time expiry, cleanup, and target authorization.

## Non-Goals

- Do not implement OCR, image editing, thumbnails, video evidence, malware-provider integration, retention deletion, public sharing, Shopify media publication, receipts accounting, or QR labels.
- Do not store file bytes, base64 content, grant tokens, or presigned URLs in PostgreSQL.
- Do not expose the local storage directory through static web serving.
- Do not make S3, AWS, MinIO, or any provider authoritative for file relationships or workflow state.
- Do not add automatic cleanup workers; SF-05 supplies durable jobs.
- Do not modify Machine/Load tables directly from Files. Use the exported Inventory operations to validate targets.
- Do not add a second authorization or database client.

## Implementation Plan

1. Extend config/contracts/permissions with secure defaults: local adapter in development/test, S3 required for staging/production unless an explicit local override is set, five-minute upload grants, one-minute download grants, and a configurable 15 MiB maximum.
2. Add attachment, one-time grant, and immutable activity schema/migrations. Enforce exactly one target and controlled state/purpose/action values in PostgreSQL.
3. Define `StorageAdapter` (`put`, `head`, `get`, `delete`) and implement local filesystem plus S3-compatible adapters. Local writes are confined under the configured root; S3 uses generated keys and private objects.
4. Implement one Files service owning target authorization, content policy, grant issuance/consumption, generated keys, SHA-256, transitions, failure handling, and cleanup.
5. Implement bounded multipart upload and streamed/buffered download endpoints. Never log content/grants; set safe content type/length/disposition and `Cache-Control: private, no-store`.
6. Add integration tests using a disposable local directory and real sessions. Assert database metadata, adapter head/read bytes, checksum, activity, and state agree.
7. Add attachment panels/clients to Machine and Load details with accessible upload/download/failure/empty states.
8. Run full root gates and verify existing identity/inventory behavior remains unchanged.

## Constraints

- Preserve private-by-default access. A storage key is not a public URL and is never returned by general metadata/list endpoints.
- Access grants are at least 256 bits of randomness, stored only as SHA-256 hashes, bound to user/file/operation, short-lived, and atomically consumed once.
- The upload route requires both the issuing signed-in user and the valid upload grant. The download route likewise rechecks current file/target permission before consuming the grant.
- Multipart memory buffering is allowed only with the configured hard limit; reject before storage when declared or actual size exceeds it.
- Detect actual bytes; a `.jpg` filename or declared `image/jpeg` is not evidence of type.
- Object key format uses generated IDs only. Reject path traversal in the local adapter even though callers should never supply arbitrary keys.
- The database cannot atomically commit with object storage. Make ordering and recovery explicit: object write/head first, then ready metadata/activity; a failure remains visible and cleanup-safe.
- Do not mark `ready` until stored byte count, detected media type, and SHA-256 match the recorded values.
- Treat adapter errors as safe internal failures; do not expose credentials, endpoints, bucket details, raw SDK errors, local paths, tokens, or file bytes.
- S3 credentials may use the standard provider chain; if explicit access key/secret are configured, require the pair without logging either.
- Filename output must resist CR/LF and quote injection. Grant query/header values must not appear in logs.
- No object/file hard deletion through ordinary staff UI. Abandonment is a state transition with activity; cleanup removes only non-ready objects.

- Authorized staff can upload and later download a real Machine nameplate photo through short-lived one-time grants; unauthorized users cannot issue or consume grants.
